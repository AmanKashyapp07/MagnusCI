│                                BULLMQ JOB LIFECYCLE STATE MACHINE                                │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

        [ Ingress Webhook ]
                 │
                 ▼
          ┌─────────────┐
          │   WAITING   │ ◄─── (Job enqueued with payload & options)
          └──────┬──────┘
                 │
                 │ Worker claims job via atomic Lua BRPOPLPUSH
                 │ Lock acquired: lockDuration = 300,000ms (5 min)
                 ▼
          ┌─────────────┐
          │   ACTIVE    │ ◄─── Heartbeat renews lock every 30s
          └──────┬──────┘
                 │
      ┌──────────┴──────────┐
      │                     │
      │ Job succeeds        │ Stage returns exit != 0 or worker crashes
      ▼                     ▼

## 3. Worker Concurrency & Stalled-Job Heartbeat Watchdog

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                         WORKER CONCURRENCY & STALLED-JOB WATCHDOG                                │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘

  [ Worker Process 1 ] ── Holds Job A lock (TTL = 300s)
           │
           ├── T = 0s:   Worker starts container execution
           ├── T = 30s:  Heartbeat extends lock TTL to 300s
           ├── T = 60s:  Worker killed abruptly (OOM / SIGKILL / Host Crash)!
           │             Lock heartbeat CEASES immediately!
           │
  [ BullMQ Stalled-Job Watchdog (Runs every 30s across cluster) ]
           │
           ├── T = 90s:  Watchdog checks Redis: Lock still valid (expires at T = 330s)
           ├── T = 330s: Redis lock EXPIRES! Job is now marked STALLED.
           │
           ▼
  [ Automated Recovery Action ]
   1. Stalled job checker detects abandoned active job with expired lock
   2. Increments `stalledCount` (maxStalledCount: 2)
   3. Moves Job A from active back to WAITING queue
   4. Worker Process 2 claims Job A and restarts execution cleanly
   RESULT: Zero orphaned builds; self-healing without manual operator intervention!
```

## 4. Concurrency & Persistence Failure Matrix

| Failure Mode | Root Cause | System Defense | Impact / Recovery |
| :--- | :--- | :--- | :--- |
| **Worker Host OOM Crash** | Pipeline stage exceeds container cgroup limits or leaks memory | Docker cgroup hard ceiling (1GB-2GB) kills container with exit 137; Worker stays alive | Worker records OOM status in DB; BullMQ job marks failure cleanly. Host VM protected. |
| **Worker Process `SIGKILL`** | Pod evicted by Kubernetes scheduler during rolling deploy | BullMQ stalled job watchdog (30s check, 300s TTL lock) | Job re-queued to healthy worker after lock expiration; build restarts. |
| **Redis Connection Drop** | Redis pod crash or network partition | `ioredis` exponential retry backoff; Express gateway buffers requests | Ingress retries up to 3 times before returning HTTP 503; zero crash loops. |
| **PostgreSQL Pool Saturation** | Spike in concurrent builds flooding log queries | Connection pool capped at `max: 25`; `connectionTimeoutMillis: 2000` | Queries fail fast with 500 error rather than hanging worker event loop. |
| **Log Write Amplification** | Verbose compilation emitting 1,000+ lines/sec | In-memory 1000ms debouncing (`setInterval(..., 1000)`) in `worker.js` | 95% reduction in SQL `UPDATE` writes; WAL disk saturation prevented. |

## 5. Rapid Interview Talking Points (60 Seconds)

- **Decoupled Architecture:** Webhooks are acknowledged with HTTP 202 in $< 10\text{ms}$; execution is deferred to BullMQ workers, protecting the API event loop.
- **Concurrency Budgeting:** Worker daemon runs with `concurrency: 1` build per pod, matching runner CPU/RAM capacity (1 container = 1 vCPU / 2GB RAM).
- **Stalled Job Self-Healing:** Distributed locks with 300-second TTL and 30-second watchdog checks guarantee builds are never lost if a worker pod crashes.
- **Database Safety:** PostgreSQL pool of 25 connections with 2-second timeout combined with 1000ms log write debouncing protects DB throughput during bursts.
